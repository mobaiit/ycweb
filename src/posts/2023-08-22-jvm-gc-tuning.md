---

八月中旬，监控告警：某个服务的 P99 响应时间每隔三到四小时会出现一次尖刺，从平时的 200ms 附近突然飙升到 2000ms 以上，持续大约一分钟后恢复正常。

规律性的尖刺，不是随机抖动。这种规律性本身就是一条线索——某种周期性的内部行为在导致它，而不是外部流量的变化。

我的第一反应：GC。

---

## 确认直觉

在 JVM 启动参数里加上 GC 日志输出：

```
-Xlog:gc*:file=/var/log/app/gc.log:time,uptime:filecount=5,filesize=20m
```

重启服务，等了将近四小时，打开日志，搜索"Pause Full"：

```
[4h03m12s] GC(1523) Pause Full (Ergonomics) 3820M->1245M(4096M) 54321ms
```

找到了。全停顿 GC，持续时间 54 秒。54 秒内所有的应用线程全部暂停，所有进来的请求全部积压，等 GC 结束才能继续处理。

告警里那个"持续一分钟的延迟尖刺"，就是这个。

Full GC 从 3820M 回收到 1245M，说明老年代撑满了才触发。问题变成：什么东西在不断地往老年代里堆积，直到把它堆满？

## 堆快照分析

用 `jmap` 抓一次堆快照：

```bash
jmap -dump:live,format=b,file=heap-$(date +%Y%m%d%H%M%S).hprof <pid>
```

把文件下载下来，用 Eclipse MAT 打开，看 Dominator Tree——占用内存最多的对象是谁。

排名第一的：一个 `HashMap<String, List<TradeRecord>>`，占了将近 2G。

点进去，查找它在代码里的引用，找到了：

```java
// 本地缓存，存储最近的查询结果
private static final Map<String, List<TradeRecord>> queryCache = new HashMap<>();
```

找到了根因：这是一个本地缓存，设计意图是缓存最近的查询结果，避免重复查库。但它没有设置最大容量，没有设置过期时间，没有任何淘汰机制。随着时间推移，缓存里的数据只进不出，无限增长，直到把老年代填满，触发 Full GC。

写这段代码的人（不是我）当时大概是这么想的：缓存的 key 是查询参数的 hash，数量应该有限。但他没有考虑到：查询参数是用户输入的，组合可以是无穷无尽的，不同用户的不同查询会不断产生新的 key。

**无界的本地缓存，本质上是一种内存泄漏。**

## 修复

两步。

第一步，用 Guava Cache 替换裸 HashMap，加上容量限制和过期时间：

```java
private static final Cache<String, List<TradeRecord>> queryCache =
    CacheBuilder.newBuilder()
        .maximumSize(5_000)          // 最多缓存 5000 个 key
        .expireAfterWrite(10, TimeUnit.MINUTES)  // 写入 10 分钟后过期
        .recordStats()               // 开启统计，监控命中率
        .build();
```

`maximumSize` 超出后自动使用 LRU 淘汰最久未使用的条目；`expireAfterWrite` 保证数据不会永远驻留在内存里。

第二步，调整 JVM 参数，换成 G1 GC，设置最大停顿目标：

```
-Xms4g -Xmx4g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:G1HeapRegionSize=16m
```

G1 会把堆划分成多个区域，每次只回收部分区域，用可预测的停顿时间换取吞吐量，不会像 CMS 或 Serial Old 那样在老年代撑满时来一次大暂停。

上线之后观察了一周，Full GC 消失，P99 响应时间稳定在 150ms 以内，再没有出现过尖刺。

## GC 告警

这件事里另一个值得复盘的地方：这个问题存在了多久？

GC 日志里最早的 Full GC 记录可以追溯到上线后大概两周。也就是说，它已经默默发生了两周，每隔几小时让服务卡顿一分钟，没有人注意到，直到有用户反馈说"你们系统有时候很慢"，监控里才有人专门去看。

事后我补充了 GC 相关的告警：Full GC 次数超过阈值，GC 停顿时间超过阈值，老年代使用率超过 80%。这些指标如果从一开始就有，会早得多发现问题。

监控不是出了事之后的救命稻草，是日常运营的基础设施。没有监控的系统，你不是在运维它，你是在赌它不出事。

## JVM 内存模型不是可选知识

这次排查的每一步，都建立在对 JVM 内存模型的理解上：新生代和老年代的作用是什么，对象什么时候会晋升到老年代，Full GC 在什么情况下触发，G1 和 CMS 的区别是什么，停顿时间目标的含义是什么。

如果这些概念只是模糊地"知道有这么回事"，排查会慢得多，甚至会走弯路——改了 GC 参数，发现没用，因为根本没有找到根因；或者找到了内存泄漏，但不知道怎么验证修复是否有效。

**基础知识在出问题的时候会加倍地体现出价值。** 平时觉得这些底层的东西用不上，只有真正卡在一个问题里，才会感受到理解深度的差距。

---

那次排查结束之后，我在内部 Wiki 上写了一篇文档，记录了整个排查过程、根因分析、修复方案，以及补充了哪些监控。

不是为了表功，是为了下次有人遇到类似的问题，能有一个起点，不用从头摸索。

每一次出问题，都是一次留下痕迹的机会。痕迹多了，系统就有了历史，有历史的系统，比没有历史的系统更容易被人理解和维护。

这件事本身，也是一种对代码的善意。
