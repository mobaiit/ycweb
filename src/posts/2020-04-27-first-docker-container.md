在学 Docker 之前，我经历过一种折磨，叫做"环境配置"。

大概是大三的事。和同学合做一个课程项目，代码在我的电脑上跑得好好的，发给他之后，他发来一条消息："你这跑不起来。"

然后开始了漫长的排查。JDK 版本不一样——他装的是 1.8，我用的是 11。MySQL 版本不一样——他的是 5.7，我的是 8.0，有几个 SQL 语法不兼容。端口冲突——他电脑上 8080 端口被另一个进程占着，启动直接报错。

调了三个多小时，问题一个一个排掉，最后终于跑起来了。

那天晚上我坐在桌子前，对着屏幕发了很久的呆。心里有一种说不清楚的不对劲——这种问题不应该存在。代码是我写的，逻辑是正确的，为什么换一台电脑就变成了不可预测的黑盒？

## docker run hello-world

后来接触到 Docker，是在一篇讲微服务部署的博客里。作者提到"容器化"，说容器能把程序和它的运行环境一起打包，搬到哪里都能跑。

我当时的第一反应是：这不就是我要的东西吗。

按照文档装上 Docker，第一个命令：

```bash
docker run hello-world
```

终端里打出来一段话，大意是安装成功，Docker 能正常工作了。

没什么了不起，但我盯着那段文字想了一会儿。这意味着这个 hello-world 程序——不管它依赖什么环境，需要什么运行时——都被封装在一个镜像里，我不需要在自己电脑上安装任何东西，Docker 拉下来直接跑。

**换一台机器，再跑一次，结果一样。**

这件事听起来简单，但解决的是一个根本性的问题：环境不一致。

## 写第一个 Dockerfile

那个周末，我把自己之前做的那个课程项目容器化了。

```dockerfile
FROM openjdk:11-jre-slim
WORKDIR /app
COPY target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

六行。就这六行，把整个应用和它需要的 JDK 环境打包在一起。

第一次执行 `docker build -t my-app .`，看着命令行里一层一层地构建，最后输出 `Successfully built`。然后 `docker run -p 8080:8080 my-app`，打开浏览器，localhost:8080，页面出来了。

我把这个镜像发给同学，他 pull 下来直接跑，没有任何环境问题，第一次就成功了。

那一刻，我突然觉得之前那三小时调环境的经历变得荒唐起来——那些时间本来是不需要浪费的。

## 理解分层

Docker 的镜像是分层的，每一行 Dockerfile 指令对应一层。

这个设计乍看只是实现细节，但背后有很深的工程考量。分层意味着可以缓存——如果我修改了代码但没有改依赖，重新构建的时候，依赖那一层不需要重新下载，直接用缓存。大项目的构建时间因此可以从几分钟降到几十秒。

理解分层之后，我开始有意识地优化 Dockerfile 的指令顺序：把不常变化的层放前面（基础镜像、依赖安装），把常变化的层放后面（代码复制）。这样日常开发构建都很快。

看起来是小技巧，但背后是对"变化频率"的思考——哪些东西是稳定的，哪些东西是经常变动的，把它们分开对待。这个思路在代码设计里也同样有用。

## 隔离这件事

Docker 真正改变我思维方式的，不是"部署方便了"，而是它关于隔离的哲学。

每个容器都是一个独立的世界。它有自己的文件系统，有自己的网络命名空间，有自己的进程空间。它不依赖宿主机的环境，也不污染宿主机。你可以在同一台机器上同时跑两个使用不同版本 JDK 的应用，互不干扰。

这种隔离带来了一种清洁感——系统的每一部分都在自己的边界里，职责清晰，互不侵犯。

后来我学微服务，学 K8s，在概念上一直能找到这个隔离哲学的影子。好的系统设计，往往是在合适的地方画出合适的边界。

---

那个周末容器化完项目之后，已经是后半夜了。

窗外有零星的雨声。我把笔记本合上，感觉脑子里有什么东西咔哒一声对齐了——不是某个具体的技术概念，而是一种更宽泛的直觉：好的工具应该消除不必要的摩擦。

把时间花在真正重要的问题上，而不是花在"为什么这台机器跑不起来"上。

这件事听起来像常识，但真正做到很难。
