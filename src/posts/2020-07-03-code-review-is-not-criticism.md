实习第二周，我在同事的 PR 里留了一条评论，大意是：这个方法有七个参数，建议重构成 Builder 模式或者拆分职责；另外方法名 `doProcess` 完全不表达语义，它到底在处理什么。

对方沉默了大半天，后来只回了一句："改了，你看下。"

旁边坐着的同事悄悄跟我说："你评论太直接了，他心里不好受。"

我没有道歉。但我也在想这件事：我说的是错的吗？还是方式有问题？还是这两件事其实不矛盾，我说的是对的，但方式确实可以更好？

想了很久，没有想清楚。那时候对"沟通"这件事的理解还很浅，只知道代码写得不好就是不好，不知道怎么把"不好"这件事说得让人愿意听。

## 代码洁癖从哪里来

我对代码质量的执念，大概是从第一次接手别人代码的时候开始的。

接手的那个项目，方法名清一色是 `doXxx`、`handleXxx`、`processXxx`，几乎没有一个名字能告诉你这个方法具体做了什么。注释几乎不存在，偶尔有一行注释，内容是"处理业务逻辑"——这句话和没写没有区别。一个 Service 类将近两千行，上下文在十几个私有方法之间跳来跳去，追一条调用链能追二十分钟。

我花了整整一周才基本摸清楚这套系统的脉络。

那一周结束的时候，我心里有一种很强烈的感受：这是在浪费彼此的时间。写代码的人省了命名和重构的功夫，但读代码的每一个人——包括六个月后的他自己——都要为这个懒惰付出代价。

**代码是写给人读的，不只是给机器执行的。** 这不是什么高深的道理，但真正把它内化需要时间。

## 七个参数的方法

回到那条评论。

一个方法有七个参数，表面上看只是"参数多了点"，但往深处想，这意味着这个方法的职责可能太宽了——它同时依赖太多外部输入，说明它在做的事情超过了一件。

调用这个方法的人需要搞清楚每个参数的意义和顺序，参数类型如果相同的话，写错位置的顺序编译器还查不出来，只能等到运行时出 bug 才发现。

Builder 模式的好处不是减少参数数量，而是让参数有了名字——`OrderBuilder.productId(xxx).quantity(xxx).userId(xxx).build()`，每个参数在干什么，一目了然。

我那条评论说的是这个逻辑。但我没有说清楚"为什么"，只说了"建议怎么做"。这是当时我的盲区——以为把问题指出来就够了，不知道"解释原因"才是让人真正信服、愿意改变的关键。

## 被 Review 的那次

三个月后，技术负责人 review 了我的代码，留了十几条评论。

其中一条很刺眼："你在循环里查数据库，N+1 问题，数据量大了之后性能会很差。"

我当时的第一反应有一点点防御——觉得这个场景下数据量没那么大，应该还好。但我忍住了，没有说出来，而是先去查了 N+1 问题的文档，自己测了一下，发现当数据量到几千条的时候，响应时间确实从 50ms 涨到了将近 2 秒。

改完之后性能提升了接近十倍。

那一刻我真正理解了：Code Review 不是攻击，是另一双眼睛帮你看到你看不见的角落。我们每个人在写代码的时候都有盲区，有思维惯性，有"这样应该没问题吧"的自我宽容。别人的眼睛能打破这种自我宽容。

**接受批评比给出批评难，但也更重要。**

## 后来的方式

工作几年后，我的 Code Review 风格改变了很多。

还是会指出问题，但现在会花时间解释为什么这是个问题，以及建议怎么改。不会只写"这里不好"，会写"这里这样写会导致什么问题，可以考虑这种方案，原因是……"。

区分 blocker 和 nit——有些问题是必须改才能合并的，有些只是个人风格偏好，可以讨论，不强制。

而且我开始意识到，写评论时的语气比内容更重要。同样的意思，"这个命名不够清晰，建议改成 `calculateTotalPrice`"和"这命名根本看不懂"，技术内容完全一样，但前者是在讨论问题，后者是在评价人。

---

Code Review 这件事，我大概花了两年多才真正做对。

不是技术上的"对"，而是作为一种沟通方式的"对"——有效传递自己的判断，同时让对方真正理解，愿意改，而不只是应付了事。

那位第一次被我评论的同事，后来有一次跑来问我一个架构问题，聊了将近一个小时。最后他说，虽然当时那条评论让他不爽，但改了之后确实代码清晰了很多，他现在写代码会更多想想命名的事。

那是我工作头一年里，少数几个让我觉得"值了"的时刻之一。
