做了将近一年的 AI Agent 项目，遇到的技术问题里，记忆管理是最隐蔽的一类。

不是最难，是最容易被忽略——早期 demo 阶段不会暴露，用户量上来之后才开始出现各种奇怪的症状：Agent 回答早期问题的时候开始出错，响应时间越来越慢，偶尔出现 token 超限的报错。

六月初，我把这些问题专门花了一周时间整理清楚，记录下来。

---

## 问题是怎么出现的

这个 Agent 是一个面向内部使用的技术问答助手，接入了公司的知识库，用户可以用自然语言提问，Agent 检索相关文档，结合上下文给出回答。

早期测试的时候，每次对话都是一问一答，完全独立，没有会话概念。上线之后，用户很快反馈：能不能记住我之前说了什么，不然每次都要把背景重新说一遍。

合理的需求。我加了会话记忆，把每次对话的历史塞进 prompt 里，传给 LLM。

短期内效果很好。但三个月后，问题出现了。

某些对话 session 跑了很多轮之后，响应时间从 2 秒变成了 8 秒。偶尔出现报错：`This model's maximum context length is 8192 tokens`。仔细查了一下，原因是我把完整的对话历史都塞进 prompt 了，对话轮数多的 session，历史记录本身就超出了 token 限制。

## 记忆的三种层次

真正解决这个问题之前，我花时间把"记忆"这个概念想清楚了。

**短期记忆**：当前对话的上下文。用户在这次对话里说了什么，Agent 回答了什么，这些信息需要在对话过程中持续可用。

**长期记忆**：跨会话的信息。用户上次告诉我他们团队用的是 Java 17，这次问问题的时候我应该还记得，不需要他重新说。

**外部知识**：知识库、文档、数据库里的内容。不是"记忆"，是"检索"，需要的时候去找，不需要全部装进 prompt。

我之前的做法是把三种都扔进 prompt，导致 prompt 无限膨胀。

## 分层管理

解决方案是分层，每层用不同的策略。

**短期记忆用滑动窗口**：只保留最近 N 轮对话，不保留完整历史。大多数情况下，超过 10 轮之前的对话内容已经和当前问题关系不大了。

```python
from langchain.memory import ConversationBufferWindowMemory

memory = ConversationBufferWindowMemory(
    k=8,  # 保留最近 8 轮
    return_messages=True,
    memory_key="chat_history"
)
```

**长期记忆用摘要压缩**：当对话轮数超过阈值，把早期的对话历史压缩成一段摘要，存储摘要而不是原文。摘要保留关键信息，大幅减少 token 占用。

```python
from langchain.memory import ConversationSummaryBufferMemory

memory = ConversationSummaryBufferMemory(
    llm=llm,
    max_token_limit=1000,  # 超过 1000 token 就压缩
    return_messages=True
)
```

**用户偏好单独存储**：用户明确告诉 Agent 的信息（比如"我们团队用 Java"），单独抽取，存到数据库里，每次对话开始时作为系统提示注入，不进入滚动窗口。

这三层分开之后，prompt 的大小变得可控，长对话的响应时间恢复正常，token 超限报错消失了。

## 另一个问题：遗忘什么，记住什么

解决了技术问题之后，还有一个更有意思的问题：什么信息值得被记住？

不是所有的对话都值得保留。用户随口问了一句"现在几点了"，这条记录记进去只是噪音。用户说"我在做一个关于 K8s 监控的项目，最近在看 Prometheus"，这个值得记。

我加了一个轻量的信息提取步骤：每轮对话结束后，用 LLM 做一次判断，看这轮对话里有没有值得长期记忆的关键信息。有的话，抽取并存储；没有的话，只进滑动窗口。

```python
def extract_key_info(conversation_turn: str) -> str | None:
    """从一轮对话里提取值得长期保存的信息"""
    response = llm.invoke(
        f"""判断以下对话是否包含值得长期记忆的用户信息（技术栈、项目背景、个人偏好等）。
        如果有，以一句话总结；如果没有，返回 null。
        
        对话：{conversation_turn}"""
    )
    result = response.content.strip()
    return None if result.lower() == "null" else result
```

这个步骤多了一次 LLM 调用，有成本，但对于长期使用的用户，体验提升是明显的。

## 感受

这件事让我对 LLM 应用的工程本质有了更清楚的认识。

LLM 本身只是一个无状态的函数：给一段文本，输出一段文本，没有记忆，每次调用都是全新的。你以为它"记住"了什么，实际上是你在每次调用的时候把"记忆"作为输入的一部分传进去了。

这意味着记忆管理完全是工程层面的问题，不是模型的能力。怎么存，存多少，存什么，什么时候忘，什么时候检索——这些决策都由你来做。

**上下文工程**，某种程度上是 LLM 应用里最核心的工程挑战之一，但很多人在讨论"哪个模型更强"的时候，忽略了这一层。
