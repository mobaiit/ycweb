---

入职第一家公司，接手一个已经跑了两年的项目，第一件事是打开 git log 看看历史。

屏幕上滚出来的东西让我沉默了几秒：

```
fix
update
修改
asdfasdf
改了个东西
周五下班前提交
修复bug
修改了一些逻辑
```

一百多条 commit，几乎没有一条告诉我它做了什么。日期有，作者有，就是没有内容。

这不是版本历史，这是一堆没有意义的时间戳。

我问了当时的前辈，这个项目如果出了问题需要回滚，怎么找到要回滚到哪个版本？他想了一下说："基本上靠猜，或者挨个看 diff。"

---

一个月后，线上出了一个 bug，某个数据计算结果不对，但偶发，没有稳定复现的路径。

前辈和另一个同事排查了两天，没找到原因。我提议用 `git bisect` 二分查找。

```bash
git bisect start
git bisect bad HEAD         # 当前版本有问题
git bisect good v2.1.0      # 这个版本没问题
```

Git 自动帮你切到中间某个 commit，你测试，告诉 Git 这个版本是好的还是坏的，它继续二分。大概十几次之后，精确定位到了引入 bug 的那一个提交。

找到了，看 diff，问题一目了然——某个边界条件的处理逻辑被悄悄改掉了，改的人可能自己都没意识到影响了什么。

commit 信息写的是什么？"修改业务逻辑"。

如果那条信息写的是"调整订单金额计算中的折扣边界处理逻辑"，我还能更快地定位，而不是看到 diff 之后还要花时间理解改了什么。

**Git 的 log 不只是给现在的你看的，是给六个月后忘了所有上下文的你看的，也是给接手这个项目的陌生人看的。**

## 什么是好的 commit 信息

我后来总结的标准很简单：读 commit 信息的人，不看 diff，能不能明白这次提交做了什么、为什么做。

好的样子大概是这样：

```
feat(order): 新增订单超时自动取消功能

超时时间通过配置中心动态配置，默认 30 分钟。
使用 Redis 延迟队列实现，避免定时任务轮询的性能损耗。
关联 issue #234。
```

不需要每条都写这么详细，但至少第一行要让人知道这是在做什么事情，是新功能、修 bug、还是重构。

Angular 规范的 commit 格式是一个不错的起点：`类型(范围): 描述`。类型常用的有 feat、fix、refactor、docs、chore，范围是模块名，描述是这次改动的核心内容。不需要严格照搬，理解背后的逻辑，根据项目实际情况调整。

## 分支策略

我用的分支模型不算复杂：

`main` 永远是可以直接发布的状态，任何时候合进来的代码都应该是经过测试和 review 的。`dev` 是开发集成分支，多人协作在这里汇合。功能分支从 `dev` 切出来，命名 `feat/xxx`，做完了提 PR 合回 `dev`。紧急修复从 `main` 切，修完了同时合回 `main` 和 `dev`，打上 hotfix 的标签。

没有 gitflow 那么繁琐，但也有足够的结构。

有一个细节：功能分支在合并之前，我习惯先 rebase 到最新的 `dev` 上，把冲突在本地解决掉，再提 PR。这样 reviewer 看到的是一个干净的、基于最新代码的分支，不会夹杂着陈旧的合并冲突。

## rebase 还是 merge

这个问题我见过很多次争论，每次都很激烈。

我的立场：不教条。

功能分支合并到主干，用 merge，保留合并节点——能看清楚什么时候、什么功能合进来的，历史是真实的，没有被改写。本地同步主干的最新代码，用 rebase——把你的提交接到主干最新的后面，历史线性，之后用 bisect 也方便。

不是非此即彼，是各有适合的场景，理解了原理就知道什么时候用哪个。

---

现在每次开始一个新项目，第一件事是约定 commit 规范和分支策略，写进 README 里。

不是因为流程重要，而是因为这些约定在出问题的时候会救你。线上 bug 压着，你需要在两百个 commit 里找到那个引入问题的变更，这时候你会非常感激三个月前那个认真写 commit 信息的自己。

代码库的历史记录是一种对话——过去的你在和未来的你说话。

值不值得说清楚，取决于你觉得未来的那个人值不值得被好好对待。
