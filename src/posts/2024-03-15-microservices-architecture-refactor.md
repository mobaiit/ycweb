## 为什么要重构

接手这个项目的第一周，我就知道它必须被重构。

单体应用已经膨胀到 20 万行代码，模块之间的依赖像意大利面条一样纠缠。每次上线都是一场赌博，改一个接口可能引发连锁崩溃。团队其他人习惯了这种混乱，但我受不了。

**代码不应该是将就的产物，它应该有结构、有美感、有可预测性。**

## 拆分策略

很多人以为微服务就是把代码按模块拆开，这是最大的误区。拆分的本质是**重新定义边界**。

### 领域驱动的拆分

我没有按技术层拆（Controller / Service / DAO），而是按业务领域：

- **用户服务**：认证、权限、用户画像
- **订单服务**：下单、支付、物流
- **库存服务**：商品管理、库存扣减
- **通知服务**：消息推送、邮件、短信

每个服务都是一个独立的业务单元，拥有自己的数据库，通过 API 网关统一对外暴露接口。

### 数据一致性

分布式系统最大的挑战是数据一致性。我的方案：

1. **本地事务优先**：能在单服务内完成的操作，绝不跨服务
2. **Saga 模式**：长事务拆成多个本地事务 + 补偿机制
3. **最终一致性**：用消息队列（RabbitMQ）解耦服务间通信

没有完美的方案，只有适合业务场景的权衡。

## 技术栈选型

- **Spring Cloud**：服务注册、配置中心、熔断降级
- **Docker + Kubernetes**：容器化部署，自动扩缩容
- **Redis**：分布式缓存 + 分布式锁
- **ELK Stack**：日志聚合与追踪

选择 Spring Cloud 不是因为它最新，而是因为它在 Java 生态中最成熟。我不追求炫技，只追求稳定。

## 遇到的坑

### 1. 服务雪崩

上线第二天，订单服务挂了，导致整个调用链全部超时。

**解决**：引入 Hystrix 熔断器，设置超时阈值和降级逻辑。宁可部分功能不可用，也不能让整个系统崩溃。

### 2. 分布式事务的复杂性

Saga 模式理论优雅，实现起来全是细节。每个补偿逻辑都要仔细设计，否则会出现数据不一致。

**我的原则**：能避免分布式事务就避免。重新设计业务流程，让它天然支持最终一致性。

### 3. 日志追踪

微服务环境下，一个请求可能跨越 5 个服务。出问题时根本不知道在哪个环节炸了。

**解决**：用 Sleuth + Zipkin 做链路追踪，给每个请求分配唯一 TraceID，所有日志都带上这个 ID。

## 性能提升

重构后的效果：

- **响应时间**：从平均 800ms 降到 120ms
- **吞吐量**：从 1000 QPS 提升到 8000 QPS
- **可用性**：从 95% 提升到 99.9%

数字不会说谎。好的架构会说话。

## 教训

1. **不要过度设计**：一开始我想做服务网格（Service Mesh），后来发现团队 hold 不住，果断放弃。技术要为业务服务，不是为了炫技。

2. **文档是救命稻草**：微服务架构复杂度高，没有清晰的文档，后人会骂死你。我写了详细的架构图、API 文档、故障处理手册。

3. **监控比代码重要**：系统上线后，我花了一周搭建 Prometheus + Grafana 监控体系。没有监控，微服务就是黑盒。

## 最后

重构不是推倒重来，而是在理解系统本质后，用更优雅的方式重新实现。

**代码是写给人看的，顺便让机器执行。** 如果你的代码只有你自己能看懂，那它就是垃圾。

凌晨三点，最后一个服务部署完成。看着 Kubernetes Dashboard 上所有 Pod 都是绿色，关机，看海。
