三月初，OpenAI 开放 GPT-4 API，我当天申请，当晚拿到 key，开始写代码。

这不是追风口的行为。我是真的花时间想过：这一波 LLM 和之前的 AI 炒作有什么本质区别。

之前的 AI 模型，大多数需要大量标注数据，需要针对特定任务精心设计 pipeline，需要微调，需要你是 ML 背景的人才能用得好。换一个任务，重新来过。

GPT-4 不一样。它的核心能力是理解和生成自然语言，而且可以通过 prompt 直接指定任务。你不需要标注数据，不需要微调，不需要训练——你只需要把任务描述清楚，它就能做。

**这让"理解自然语言并执行任务"第一次变成了一件可以工程化的事情。** 不再需要 ML 专家，一个会写代码的人就可以构建能理解语言的系统。

这是根本性的变化，不是量变。

---

## 什么是 Agent

用一句话：Agent 是一个能在循环里感知、决策、行动的系统。

普通 LLM 调用是单轮的：给一个 prompt，拿一个输出，结束。

Agent 是多轮的：LLM 输出一个行动，系统执行这个行动，把结果反馈给 LLM，LLM 根据结果决定下一步，继续执行，直到任务完成。中间可以调工具：查数据库、调 API、写文件、运行代码。

最简单的 Agent 框架是 ReAct（Reasoning + Acting）：让模型交替输出思考过程（Thought）和要执行的动作（Action），观察结果（Observation），再继续思考。

这个模式非常直接，但它让 LLM 从一个文本生成器变成了一个可以与外部世界交互的主体。

## 第一个真实 Agent：代码 Review 助手

需求来自真实痛点。团队代码量大，PR 提交频繁，人工 review 经常跟不上，有些 PR 挂着三四天才有人看。

我设计了一个 Agent：

1. 监听 GitLab 的 webhook，新 PR 创建时触发
2. 拉取 PR 的 diff
3. 调用 GPT-4 分析代码变更，找潜在问题
4. 把分析结果作为 comment 写回 PR

核心代码很直接：

```python
def review_pr_diff(diff: str) -> list[dict]:
    client = OpenAI()
    response = client.chat.completions.create(
        model="gpt-4",
        messages=[
            {
                "role": "system",
                "content": (
                    "你是一个熟悉 Java 和 Spring Cloud 的资深开发者。"
                    "分析代码变更，找出：潜在的 bug、N+1 查询等性能问题、"
                    "安全漏洞（SQL注入、未校验的用户输入等）、过于复杂的逻辑。"
                    "只报告你有把握的问题，不要过度推断。"
                    "以 JSON 数组返回，每项包含 line、severity（high/medium/low）、message。"
                )
            },
            {"role": "user", "content": f"请 review 以下 diff：\n\n{diff}"}
        ],
        response_format={"type": "json_object"}
    )
    result = json.loads(response.choices[0].message.content)
    return result.get("issues", [])
```

上线之后跑了两周，发现了三个真实 bug，一个没有校验的用户输入（潜在注入风险），几个 N+1 查询。

不是银弹——它也产生了一些误报，对某些业务逻辑的判断有偏差。但它作为一个"多一双眼睛"的工具是有价值的，而且不会累，不会说"我今天没空 review"。

## 幻觉问题

LLM 最让工程师头疼的特性：它会信心满满地说错话。

有几次，Agent 报告了一个"严重的 bug"，但那段代码逻辑其实是正确的，只是写法不太常见，GPT-4 理解偏了。如果开发者不仔细看，可能会被这个误导。

我的解决方案：

**给每个问题加置信度字段**，让模型自己评估它有多确定，低于阈值的问题标记为"供参考"而不是"请修改"。

**few-shot 示例**，在 prompt 里放几个正确的和错误的例子，帮助模型校准判断标准。

**分类严重程度**，high severity 的才在 PR 里直接评论，medium 和 low 汇总成一个报告附在最后。减少噪音，让开发者把注意力放在真正重要的问题上。

## Prompt 工程是真正的工程

用 LLM 之前，我以为"prompt engineering"是个夸大的词，调整几句话而已，能叫工程？

用了之后改变了看法。

**如何明确任务边界**——告诉模型做什么，但更重要的是告诉它不做什么。"只报告你有把握的问题，不要过度推断"这句话，把误报率降低了将近一半。

**如何约束输出格式**——JSON 输出必须结构稳定，不然解析会失败。用 `response_format: json_object` 强制 JSON，再加上字段的 schema 描述，输出的稳定性大幅提升。

**如何处理边界情况**——diff 太大超过上下文怎么办？按文件分批处理，每批独立分析，最后聚合。模型输出内容为空怎么办？加重试逻辑，最多三次，还是空就放弃并记录日志。

这些都是普通的工程问题，只是接口是自然语言。
